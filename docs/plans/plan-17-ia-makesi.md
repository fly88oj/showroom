# §17 控制台 IA 独立设计稿（makesi）

> 第二轮评审立场：先做独立设计，等第一轮方案出现后用文末「评审检查表」对照打分。
> 三任务视角：发布者**首发 / 更新 / 查看**——其他都是干扰。

## 0. 设计哲学（与现状的最大反差）

现状是「admin 后台味」：四标签 + 管理员第五标签 + 内嵌 fieldset/对话框/textarea——多层级、多出口、多按钮。发布者 90% 的动作只关心三件事：URL、上传、状态。把控制台从「功能面板」改成「任务面板」：

- **顶区永远展示展项卡片**（状态 + 完整 URL + 关键操作）——这是默认落眼点
- **次区按需展开抽屉**（新发布 / 数据库 / 管理）——不抢戏、不藏起来
- **无 tab**——用垂直分区替代，原因是 tab 隐藏信息，需要用户先记住在哪

## 1. 理想操作流（三大任务）

### 1.1 首发（无 demo 时）
1. 登录（一键，已绑设备免密）→ 顶区空状态：「拖入第一个 tar 或点 + 新发布」
2. 拖入 tar → 自动用文件随机名作项目名 → 压缩→上传→发布 → 卡片即时出现
3. 卡片上有大字完整 URL + 复制按钮 → 复制 → 发给观众

### 1.2 更新（已有 demo）
1. 进控制台 → 看到所有卡片
2. 点卡片上「更新」→ 进入上传流（项目名/标签自动带出）→ 完成
3. URL 不变；旧版本在镜像库保留，可「回滚」

### 1.3 查看（状态/日志/DB）
1. 进控制台 → 看到卡片状态灯
2. 点卡片 → 下方抽屉展开：日志流 / 数据库 / Redis / 环境变量 / 镜像清单
3. 不切 tab——只展开当前展项的关联数据

## 3. 数据加载策略（全部自动·并发）

进入页面（任意时刻）并发拉取：

| 数据 | 端点 | 时机 | 刷新触发 |
|---|---|---|---|
| 展项清单 | `GET /_api/projects` | 立即 | 事件流收到 sr-* → 2s 去抖 |
| 镜像清单 | `GET /_api/images` | 立即 | import-end / image-rm 后 |
| 磁盘空间 | `GET /_api/space` | 立即 | import-end / image-rm 后 |
| Redis 库编号 | `GET /_api/redis-dbs` | 立即 | publish 后 |
| **服务端公钥** | `GET /_api/server-pubkey` | 首次（未签） | 永不过期（公开） |

**取消所有"刷新"按钮**。卡片下方角落显示「X 秒前更新」链接——点击即重取。这样按钮降级为可见性更弱的链接，主体是数据本身。

**事件流常驻**：进页即订阅 docker events（已有逻辑）；任何启停→卡片自动刷新。

## 4. 状态机（展项 4 态·不是 6 态）

| 状态 | 含义 | 视觉 | 卡片操作 |
|---|---|---|---|
| `online` | 容器运行中 | 绿 ● | 日志·停·更新·回滚·删 |
| `offline` | 容器停止/未启 | 灰 ● | 日志·启动·更新·回滚·删 |
| `error` | dead/重启循环 | 红 ● | 日志·删（禁用语义辅助） |
| `image-only` | 仅镜像无容器（仅上传后） | 蓝 ● | 部署·删 |

**映射**：running→online；exited/paused/created→offline；dead/restarting→error；missing→image-only。

**关键变化**：把「未部署」改名「仅镜像」——语义不再是"没部署"，而是"有产物无容器"，可点「部署」一键拉起。这是用户问题 C 的根治：现状的"未部署"既看不出能不能点，也没说明能不能部署。

## 5. 参数填写唯一原则（一处定义·处处引用）

**唯一源 = project 元数据**。首发时填写的 mem/port 写入项目元数据；后续更新/回滚自动沿用。表单字段从 5 个降到 2 个（项目名 + 镜像）。

落地：
- 卡片右侧齿轮图标 → 「设置」抽屉：内存需求 / 监听端口（写入项目元数据）
- 发布表单只填「项目名 + 镜像文件/选择」；其余走项目默认值
- 部署到新项目时一次性记入新项目元数据

**好处**：解决用户问题 B 的根因（重复填写）——同项目只在一处维护，表单意图清晰。

## 6. 最容易被忽略的 3 个交互细节

1. **登录完成后的焦点落点**：现在登录后焦点飘散。改为登录后 `focus('#btn-new-pub')`——给首次用户的下一步暗示。
2. **URL 复制的拼接**：现状复制只给 `/<project>/`，用户得自己拼基址。新方案「外部访问基址」存 localStorage（首登预填 `location.origin`，可在设置改）→ 复制时自动拼出完整 URL。
3. **删除展项的二次确认文案**：现状只说"容器、路由、数据库与凭据将一并移除"——发布者担心演示数据。改为「删除展项 X：容器与路由将停止访问；其关联数据库 X.dump 仍在「数据库备份」历史中可取回——本次操作不可恢复」。把"有救"说清，恐惧减少。

## 评审检查表（等第一轮方案出来后逐项打分）

> 每项三档：✅ 命中 / ⚠️ 部分命中 / ❌ 缺失或反向

### 用户问题逐项
- [ ] **A. 访问地址** — 是否展示完整 URL（含基址）？基址是配置项 / 写死 / 仍是 `location.origin`？有没有"复制完整 URL"按钮？
- [ ] **B. 重复参数** — 一键部署和部署两个表单的 mem/port 字段是否合并？合并到「项目设置」还是「最新发布记忆」？
- [ ] **C. 未部署语义** — 这个状态是改名/合并/删除了？「仅镜像」独立态是否独立列出并可一键部署？
- [ ] **D. 自动加载** — 是否真的消除所有"刷新"按钮？还是把它们保留只是改文案？时间戳链接方案有无？
- [ ] **E. 层级混乱** — tab vs 垂直分区？fieldset 对话框嵌入层级有没有减少？字号/间距/对齐有没有 a token？
- [ ] **F. 平台公钥** — PEM 还在顶部？还是用 `GET /_api/server-pubkey`（公开）自动取+缓存？新端点是否需要新增？

### 设计质量（隐性）
- [ ] **状态机** — 是否收敛到 ≤4 态？是否处理「仅镜像」这种半态？
- [ ] **加载策略** — 是否有"无刷新按钮"原则？事件流是否进页即订阅？
- [ ] **参数唯一源** — 项目元数据是否作为 mem/port 的记忆主体？表单字段是否减到 2 个？
- [ ] **三任务映射** — 首发/更新/查看三条路径是否各 ≤3 步完成？是否每条都有显式操作流文档？
- [ ] **首次体验** — 登录后焦点是否落在「+ 新发布」？空状态文案是否引导下一步？
- [ ] **破坏性操作文案** — 删除/重置/恢复是否说清"有救 vs 不可恢复"？
- [ ] **管理员隔离** — admin 区是否单列折叠抽屉而不是第五标签？普通用户 DOM 里有没有 admin 入口残留？
- [ ] **可访问性** — 键盘焦点环是否保留？aria-live/role 用得是否一致？状态徽章是否对色盲友好（不仅靠颜色）？
- [ ] **响应式** — 卡片网格在小屏是否塌成单列？抽屉是否能在桌面与移动端一致工作？

### 反向信号（出现任一即 ❌）
- [ ] 是否仍把「三入口并存」作为关键卖点？——设计哲学上应该收敛到单入口+智能意图
- [ ] 是否仍把「PEM 框」作为页首常驻元素？——违反 F
- [ ] 是否仍展示 `127.0.0.1` 这种内网地址给「给别人访问」的场景？——违反 A
- [ ] 是否仍要求用户自己点「刷新列表」「刷新镜像清单」「获取表清单」？——违反 D
